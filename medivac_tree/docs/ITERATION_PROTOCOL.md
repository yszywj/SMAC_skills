# 直接树迭代约定

1. **冻结基线与任务边界。** 记录父版本、树 JSON/hash、事实 schema、动作绑定源码/hash、适配器/环境版本、患者协调开关、清单 hash 和资源上限。相同 JSON 配上不同绑定器不算同一策略版本。
2. **按证据提出一个改动。** Codex 读取开发轨迹中的失败、改善及无效干预案例，输出可检验假设及对应 episode/loop，不把整局胜负自动归因于某个首次动作。每轮优先一个候选。
3. **离线检查。** 校验树无环、特征合法、叶子可绑定；重放观察检查动作合法性、路径、少量记忆变化及提案覆盖。离线输入不产生新环境回报，不能冒充反事实对局。
4. **配对开发验证。** 基线与候选用同一清单；除预先声明的候选文件外，环境、地面策略、患者协调和指标保持一致。所有运行使用新目录，保存失败与无效记录。以实际提交和引擎回执核查干预，不只数树叶命中。
5. **保留或淘汰。** n4 只作接线冒烟；后续先小批开发筛选，再让入围版本进入未看过的验证集。发布前才运行锁定的最终测试。任何已用于改规则的验证场景都转为开发材料。
6. **冻结迁移。** 未训练/调参的规模、组成或分布预先封存。树、阈值、事实计算和绑定器全冻结后才评估；同一分布换 seed 是同分布泛化，不自动成为跨域 zero-shot 证据。

最小决策证据为版本、唯一 decision_id、实际使用的特征/阈值、路径/叶子、动作绑定依据、预留患者、规则提案、最终动作及覆盖原因。观察、引擎反馈和逐局结果复用既有日志，避免重复采集。

患者预留采用确定性逐机处理时，应记录处理顺序；“冲突数为零”不能证明分配最优，也不能证明协同收益。叶子选择与行为绑定分开审计，避免复杂评分器被隐蔽转移到绑定器中。

SC2 原有 runner 每局新建进程并复用场景配置；未提供任意中途状态的恢复接口。本阶段不声称同内存反事实，也不新增这一能力。

2026-11-03 已新增可执行的“一局一次候选干预 → 观察前缀配对审计 → 收益树训练”管线，见 [配对回报学习](RETURN_LEARNING.md) 和 [验证记录](RETURN_VALIDATION.md)。该收益树只适用于同一首次机会协议，不能直接推广成每步反复修改。
